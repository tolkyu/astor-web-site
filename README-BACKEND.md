# Астор — бекенд і звʼязок з Telegram

Сайт надсилає в Telegram дві речі:

| Подія | Коли | Що приходить |
|---|---|---|
| **Заявка** | відправлено форму «Записатися на сервіс» | імʼя, телефон, опис робіт, час |
| **Клік по звʼязку** | натиснуто кнопку з номером (`tel:`) | яка саме кнопка, час, сторінка |

---

## Що потрібно від вас

Рівно **два значення** — більше нічого:

| Змінна | Що це | Де взяти |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота | @BotFather → крок 1 |
| `TELEGRAM_CHAT_ID` | куди слати заявки | крок 2–3 |

Платіжки, домени, зовнішні сервіси — не потрібні. Telegram Bot API безкоштовний.

---

## Крок 1. Створити бота і взяти токен

1. Відкрийте Telegram → знайдіть **[@BotFather](https://t.me/BotFather)**.
2. `/newbot`
3. Введіть назву, яку побачите ви: `Астор — заявки`
4. Введіть username, обовʼязково з `bot` на кінці: `astor_zayavky_bot`
5. BotFather відповість рядком виду:

```
8123456789:AAHxq1YqK7m-Nf3pLd8vT2wR5sX9zC0bE4g
```

Це і є `TELEGRAM_BOT_TOKEN`.

> **Токен = пароль від бота.** Хто його має — може писати від імені бота й читати заявки.
> Не комітьте його в git (файл `.env` уже в `.gitignore`). Якщо витік — `/revoke` у BotFather.

---

## Крок 2. Вирішити, куди слати заявки

**Варіант А — особисті повідомлення.** Найпростіше, якщо заявки дивиться одна людина.
Просто напишіть своєму боту `/start`.

> Бот **не може написати першим**. Поки ви не надіслали йому `/start`, доставка падатиме
> з помилкою `bot can't initiate conversation with a user`.

**Варіант Б — робоча група.** Краще, якщо заявки бачить кілька людей (майстер + адміністратор).

1. Створіть групу, напр. «Астор — заявки».
2. Додайте туди бота і потрібних співробітників.
3. Напишіть у групі `/start@astor_zayavky_bot` — саме з `@username`.

> У групах Telegram за замовчуванням ховає від ботів звичайні повідомлення (privacy mode).
> Команда з `@username` пробиває це обмеження — вона потрібна лише один раз, щоб
> дізнатись `chat_id`. Надсилати заявки боту це не заважає.

---

## Крок 3. Дізнатися `TELEGRAM_CHAT_ID`

Впишіть токен у `.env` (скопіюйте з `.env.example`), далі:

```bash
npm run tg:chat-id
```

Отримаєте готові рядки:

```
✅ Бот: @astor_zayavky_bot (Астор — заявки)

Знайдені чати — скопіюйте потрібний id у TELEGRAM_CHAT_ID:

  TELEGRAM_CHAT_ID=412345678          # приватний: Дмитро
  TELEGRAM_CHAT_ID=-1002345678901     # супергрупа: Астор — заявки
```

Особистий id — додатне число, груповий — **відʼємне**. Мінус є частиною id, не загубіть його.

---

## Крок 4. Заповнити `.env`

```bash
cp .env.example .env      # Windows: copy .env.example .env
```

Мінімально достатньо:

```env
TELEGRAM_BOT_TOKEN=8123456789:AAHxq1YqK7m-Nf3pLd8vT2wR5sX9zC0bE4g
TELEGRAM_CHAT_ID=-1002345678901
```

---

## Крок 5. Перевірити

```bash
npm run tg:test
```

Якщо в чат прийшло «Тестове повідомлення» — звʼязок працює, форма теж працюватиме.

Далі запуск сайту:

```bash
npm install     # один раз
npm run dev     # → http://localhost:3000
```

У консолі має бути:

```
🚗 Астор — сервер запущено
   http://localhost:3000
   telegram: ✅ @astor_zayavky_bot → чат -1002345678901
```

Відкрийте сайт, натисніть «Записатися на сервіс», заповніть форму — заявка має впасти в Telegram.

---

## Якщо запустити без токена

Сервер стартує в режимі **dry-run**: заявки валідуються, зберігаються у файл і друкуються
в консоль, але в Telegram не йдуть. Зручно для верстки, коли бот ще не потрібен.

При `NODE_ENV=production` dry-run вимкнено — сервер відмовиться стартувати з порожнім
токеном, щоб бойовий сайт не «приймав» заявки в нікуди.

## Команди бота

Сервер не лише надсилає заявки — він також слухає команди (long polling, окремого
домену чи HTTPS не потрібно):

| Команда | Що робить |
|---|---|
| `/start` | пояснює, що це за бот, і чи налаштований цей чат як отримувач |
| `/help` | список команд |
| `/id` | id поточного чату — зручно при налаштуванні |
| `/ping` | перевірка, що бот живий |

> **Бот відповідає лише поки запущено сервер.** Якщо `npm run dev` не працює —
> `/start` нічого не поверне. Це не поломка: команди обробляє саме бекенд.

> Оновлення з Telegram може забирати **лише один процес**. Якщо запустите
> другий інстанс — він отримає `409 Conflict` і вимкне polling. Для кількох
> інстансів лишіть `BOT_POLLING=1` тільки на одному.
>
> З цієї ж причини `npm run tg:chat-id` покаже порожній список, поки сервер
> працює: він уже забрав оновлення собі. Зупиніть сервер на час команди.

## API

| Метод | Шлях | Призначення |
|---|---|---|
| `POST` | `/api/booking` | заявка з форми |
| `POST` | `/api/lead` | клік по кнопці звʼязку |
| `GET` | `/api/health` | стан сервера (для моніторингу) |

**`POST /api/booking`**

```jsonc
// запит
{ "name": "Іван", "phone": "0501234567", "msg": "Skoda Octavia 2015, заміна оливи" }

// 200 — прийнято
{ "ok": true, "id": "c1583222-…" }

// 400 — помилки полів (фронтенд підсвічує їх під інпутами)
{ "ok": false, "error": "validation",
  "fields": { "phone": "Перевірте номер — очікується формат +380 XX XXX XX XX." } }

// 429 — забагато спроб з одного IP
// 502 — заявка збережена, але Telegram не прийняв (клієнту показуємо телефон)
```

Телефон нормалізується сам: `0501234567`, `380501234567`, `+380 (50) 560-03-58`
однаково перетворюються на `+380501234567`.

---

## Що вже вбудовано

- **Захист від спаму** — honeypot-поле (боти його заповнюють, люди не бачать) + ліміт
  5 заявок і 30 кліків на IP за 10 хвилин.
- **Нічого не губиться** — кожна заявка спершу пишеться в `data/submissions.jsonl`,
  і тільки потім іде в Telegram. Якщо месенджер лежав — запис лишиться на диску.
- **Екранування** — текст від відвідувача екранується перед відправкою, розмітку
  повідомлення зламати не можна.
- **Повтори** — при `429`/`5xx` від Telegram запит повторюється з витримкою.
- **Заголовки безпеки** — CSP, `nosniff`, `X-Frame-Options`.

## Публікація на Vercel

Vercel — serverless: код живе рівно один запит. Тому там інша конфігурація,
ніж локально, і потрібне зовнішнє сховище.

### 1. Змінні оточення

У Vercel → Settings → Environment Variables лишіть **тільки це**:

| Змінна | Значення |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен від BotFather |
| `TELEGRAM_CHAT_ID` | ваш id |
| `TELEGRAM_WEBHOOK_SECRET` | випадковий рядок (див. нижче) |

**Приберіть, якщо імпортували з `.env`:** `PORT`, `HOST`, `NODE_ENV`.

> `NODE_ENV` найважливіше. Vercel виставляє `production` сам, а імпортоване
> з `.env` значення `development` його перебиває — і тоді `trustProxy`
> вимикається, rate limit бачить IP проксі замість відвідувачів, і **всі
> клієнти рахуються як один**. Після 5 заявок сайт почне відмовляти всім.

`RATE_LIMIT_*` можна лишити або прибрати — вони збігаються з дефолтами.

Секрет для webhook згенеруйте так:

```bash
node -e "console.log(crypto.randomUUID())"
```

### 2. Сховище

Storage → Marketplace → **Upstash for Redis** → Connect до проєкту.
Vercel сам додасть `KV_REST_API_URL` і `KV_REST_API_TOKEN` — вручну нічого
вписувати не треба.

Без Redis у serverless не працюють дві речі: rate limit (лічильник у памʼяті
вмирає разом із функцією) і резервні копії заявок (файлова система лише
для читання).

### 3. Webhook для бота

Long polling у serverless неможливий — постійного процесу немає. Після
першого деплою вкажіть боту адресу:

```bash
npm run tg:webhook -- https://ваш-домен.vercel.app
```

Перевірити стан або відкотитись назад на polling:

```bash
npm run tg:webhook -- status
npm run tg:webhook -- delete
```

> `TELEGRAM_WEBHOOK_SECRET` має бути **однаковий** у Vercel і локально в `.env` —
> звідси команда бере його, щоб передати Telegram, а сервер ним перевіряє
> кожен вхідний запит.

### Як це влаштовано

| Файл | Роль |
|---|---|
| `server/src/app.js` | сам застосунок, без запуску |
| `server/server.js` | локально: слухає порт + long polling |
| `api/index.js` | на Vercel: той самий застосунок як функція |
| `vercel.json` | `/api/*` → функція, решта → CDN |

Перевірити, що все зійшлось: `GET /api/health` має віддати
`"serverless": true`, `"storage": "redis"`, `"botMode": "webhook"`.

## Публікація деінде (Render, Railway, Fly, VPS)

Там постійний процес, тож усе простіше — код працює як є:

1. `TELEGRAM_BOT_TOKEN` і `TELEGRAM_CHAT_ID` задайте в панелі хостингу.
2. `NODE_ENV=production`
3. За nginx / Caddy / хмарним проксі — додайте `TRUST_PROXY=1`.
4. Команда запуску: `npm start`
5. `data/` тримайте на постійному диску, інакше резервні копії заявок
   зникатимуть при кожному деплої. Або підключіть Redis — тоді `data/`
   не використовується.

## Якщо щось не працює

| Симптом | Причина |
|---|---|
| `bot can't initiate conversation with a user` | ви не написали боту `/start` |
| `chat not found` | не той `chat_id`, або загубився мінус у груповому id |
| `bot was kicked from the group` | бота видалили з групи — додайте знову |
| `npm run tg:chat-id` не бачить чатів | не написали боту; у групі потрібне `/start@username` |
| Заявки не доходять, у логах `502` | подивіться `data/submissions.jsonl` — вони там |
| Rate limit ловить одразу всіх | забули `TRUST_PROXY=1` за проксі |
| `401 Unauthorized` | токен зіпсовано або відкликано — `/revoke` у BotFather |
| **`/start` мовчить локально** | не запущено сервер — команди обробляє бекенд, не Telegram |
| **`/start` мовчить на Vercel** | не встановлено webhook: `npm run tg:webhook -- https://…` |
| `/api/*` віддає 404 на Vercel | немає `vercel.json` або теки `api/` в деплої |
| `health` показує `storage: file` на Vercel | не підключено Upstash Redis |
| Усіх клієнтів разом ловить rate limit | лишили `NODE_ENV=development` у змінних Vercel |
| `409 Conflict` у логах | оновлення читає інший процес або встановлено webhook |
| `tg:chat-id` показує порожньо | працює сервер — він забрав оновлення; зупиніть його |
