**Астор — запуск і підтримка**

Потрібен Node.js 22 або новіший. Поточний сайт: Express, серверний HTML та невеликі браузерні модулі. Зовнішні шрифти й frontend-фреймворк не потрібні.

**Локально**

1. Встановіть залежності: `npm install`.
2. Створіть `.env` за зразком `.env.example`.
3. Запустіть `npm run dev`; відкрийте `http://localhost:3000`.
4. Перевірки: `npm test` і `npm run check`. У PowerShell із заблокованими npm.ps1 використовуйте `npm.cmd`.

Без Telegram у development працює явний dry-run. Заявка зберігається, а клієнт бачить повідомлення про локальну перевірку. Production не дозволяє dry-run. Тести ізольовані, не читають .env і не надсилають справжніх повідомлень.

**Структура**

- `public/`: тільки дозволені публічні CSS, JavaScript, зображення, robots і sitemap.
- `server/templates/`: головна сторінка та адмінка.
- `server/src/site.js`: публічні контактні дані.
- `server/src/priceStore.js`: прайс, версії, захист від одночасного редагування.
- `server/src/bookings.js`: збережені заявки, ідемпотентність, повторна доставка.
- `data/`: локальні приватні дані. Ніколи не публікуйте цю директорію.
- Старі `assets/`, `_ds/`, `admin.html`, `ds-base.js`, `image-slot.js` не використовуються новим сайтом і виключені з Vercel upload. Залишені як вихідні матеріали попереднього оформлення.

**Telegram**

Задайте `TELEGRAM_BOT_TOKEN` і `TELEGRAM_CHAT_ID`. Для групи chat id зазвичай від’ємний. Додайте бота до потрібного чату; для особистого чату спершу надішліть боту /start.

Допоміжні команди:

- `npm run tg:chat-id` — знайти chat id.
- `npm run tg:test` — надсилає справжнє тестове повідомлення.
- `npm run tg:webhook -- https://ваш-домен` — налаштувати webhook.
- `npm run tg:webhook -- status` — перевірити webhook.

Не запускайте polling одночасно з production webhook того самого бота. Для локального перегляду задайте `BOT_POLLING=0`.

**Прайс і адмінка**

`/admin` — редактор прайсу, історія останніх 20 версій і список останніх 50 заявок.

Згенеруйте хеш: `npm run admin:hash -- "ваш-пароль"`; збережіть результат у `ADMIN_PASSWORD_HASH`. Сесія — HttpOnly cookie на 12 годин, SameSite=Strict, Secure у production. Production потребує HTTPS. Старі localStorage-сесії більше не приймаються.

Без Redis прайс атомарно записується в `data/prices.json`. Зміни переживають повторне читання й перезапуск. Для кількох процесів/реплік використовуйте Redis: файл призначений для одного процесу на постійному диску.

Новий ключ Redis — `astor:price-state`. Якщо його ще немає, читається старий `astor:prices`; новий запис створюється при першому збереженні. Старий ключ не видаляється. Прайс, метадані та історія записуються разом. Несумісні одночасні зміни повертають HTTP 409.

HTML прайсу має `Cache-Control: no-store`. Після збереження достатньо оновити сайт. При відмові Redis публічна сторінка може використати останню версію в пам’яті поточного процесу; холодний процес повертає помилку замість непомітної підміни дефолтними цінами. Адмінка під час відмови сховища не дозволяє збереження.

**Заявки та доставка**

Спершу заявка надійно записується, потім виконується доставка Telegram. Клієнтський ключ ідемпотентності усуває створення нової заявки під час повтору того самого запиту.

- Локально: окремі JSON-файли в `data/bookings/`.
- Redis: `astor:booking:<id>`, індекс `astor:booking-index`, черга `astor:booking-pending`.
- Невдала доставка лишає статус pending; заявка доступна адміністратору.
- На постійному сервері (`npm start`) повтор запускається щохвилини сам. На Vercel постійного процесу немає, і крона для нього теж — див. «Крони».
- В адмінці є ручний повтор доставки. На Vercel це основний спосіб.
- `GET /api/jobs/retry` — захищений повтор, заголовок `Authorization: Bearer <CRON_SECRET>`.
- Кожен запуск обробляє до п’яти заявок паралельно; блокування доставки має строк дії, щоб завислий процес не зупинив повтор назавжди.

Гарантія доставки Telegram — at-least-once: якщо Telegram прийняв повідомлення, а процес не встиг записати статус, повторне сповіщення можливе. Номер заявки в повідомленні дозволяє його впізнати. Сам запис заявки не дублюється.

Заявки не змішуються з телефонними кліками й не витісняються ними. Старі записи з `data/submissions.jsonl` / `astor:submissions` збережені, але не мігруються автоматично в новий список. Їх слід залишити як приватний архів і обробляти окремо.

**Vercel**

Публічний output — `public/`. `api/index.js` обслуговує сторінку, адмінку й API. Не змінюйте output на корінь репозиторію.

Обов’язкові змінні:

- `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`;
- `TELEGRAM_WEBHOOK_SECRET`;
- `KV_REST_API_URL` + `KV_REST_API_TOKEN` або `UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN`;
- `ADMIN_PASSWORD_HASH` — для керування й перегляду заявок.

Не задавайте `NODE_ENV=development` у production. Конфігурація перевіряється і в serverless entrypoint.

Необов’язкові, але потрібні для повної роботи агента:

- `ANTHROPIC_API_KEY` — без нього агент вимкнений, решта сайту працює;
- `CRON_SECRET` — щоденний звіт і нагадування про ТО;
- `GOOGLE_REVIEW_URL` — кнопка «Залишити відгук» після оцінки 4–5.

Для автоматичного повтору додайте `CRON_SECRET` — випадковий секрет планувальника. Без нього сайт працює, а `/api/jobs/retry`, `/api/jobs/daily-report` і `/api/jobs/service-reminders` повертають 401; ручний повтор залишається доступним авторизованому адміністратору.

На Vercel у `/api/jobs/retry` крона немає: обидва слоти Hobby зайняті нагадуваннями про ТО і щоденним звітом (див. «Крони» нижче). Недоставлена заявка лишається в статусі `pending` до ручного повтору в адмінці. Щоб повернути автоповтор — зовнішній планувальник із `Authorization: Bearer <CRON_SECRET>` або Pro і третій запис у `crons`. [Обмеження Vercel](https://vercel.com/docs/cron-jobs/usage-and-pricing).

Після розгортання перевірте: `/api/health`, доступність /admin, відсутність доступу до /data і /server, збереження прайсу, webhook, cron та одну погоджену тестову заявку.

**Аналітика та контент**

На Vercel підключається Web Analytics. Події: booking_open, booking_start, booking_success, booking_error, call, route. Поля заявки та назви робіт у події не передаються. Потрібно активувати Web Analytics у проєкті; доступність custom events залежить від налаштувань сервісу. Телефонний клік не означає підтверджений дзвінок чи запис.

Для завершення контентної частини власнику потрібні фото заїзду/команди/робіт, перевірені умови щодо матеріалів та погоджений порядок обробки й видалення даних. У коді немає вигаданих відгуків, стажу, гарантій або фотографій майстрів.

**Змінні для VPS/локального запуску**

`HOST`, `PORT`, `TRUST_PROXY` (кількість довірених proxy hops або явна мережа), `PRICE_PATH`, `BOOKING_DIR`, `BOT_POLLING`, `RATE_LIMIT_MAX_BOOKINGS`, `RATE_LIMIT_WINDOW_MS`. Зберігайте data на постійному диску та резервуйте. Redis і price history не замінюють резервну копію.

**AI-агент**

Агент приймає клієнтів у чаті на сайті (кнопка в правому нижньому куті) і в тому самому Telegram-боті, що надсилає заявки. Консультує за прайсом, збирає ім’я, телефон, авто й опис проблеми, після чого створює заявку і передає її адміністратору. Час візиту агент НЕ призначає: Google Calendar не підключений, тож адміністратор передзвонює і узгоджує сам. Побажання клієнта («у четвер по обіді») їде в заявці вільним текстом.

Потрібен лише `ANTHROPIC_API_KEY`. Без нього агент вимкнений: кнопка чату відповідає телефоном майстерні, бот поводиться як раніше, сайт і форма заявки не змінюються. Решта змінних — у `.env.example`, усі з робочими значеннями за замовчуванням.

Ціни агент називає тільки нижньою межею — «від 500 грн, точна сума після огляду». Верхня межа до моделі не доходить узагалі, тож проговоритися їй нема чим.

Прайс агент читає з того самого джерела, що й сайт: Redis через `priceStore.js`, редагується в `/admin`. Другого файлу з цінами немає свідомо — інакше ціна в чаті колись розійшлася б із ціною на сторінці. Рядки прайсу розбираються в числа (`500–1000` → від 500, `6 год – 3 доби` → 360 хв); id послуг виводяться з назв, тому переставляння рядків в адмінці їх не ламає.

FAQ лежить у `content/faq.md` і читається в системний промпт. Відповіді підтверджені майстернею 8 жовтня 2026 року. Файл правиться без участі програміста, але вимагає деплою, щоб потрапити на Vercel: агент читає його один раз за життя функції. Усе, що дописуєте, агент цитуватиме клієнтам дослівно, тож обіцянок, яких майстерня не виконує, тут бути не повинно.

Команди адміністратора в Telegram (працюють лише в чаті `TELEGRAM_CHAT_ID`):

- `/agent` — список команд і стан паузи.
- `/requests [n]` — останні заявки від агента.
- `/done <id заявки>` — роботу виконано: заявка закривається, рахується наступне ТО.
- `/service_due [днів]` — авто, яким час на ТО (типово 30 днів).
- `/pause`, `/resume` — вимкнути / увімкнути автовідповіді для всіх.
- `/reply <chat_id> текст` — відповісти клієнту від імені майстерні.
- `/resume_chat <chat_id>` — повернути агента в діалог після handoff.

Команди клієнта: `/finish` — завершити діалог і поставити оцінку; `/delete_me` — ім’я, телефон, авто й історія діалогу стираються, індекси пошуку знімаються. Уже передані заявки лишаються в роботі без персональних даних.

Handoff: при скарзі, питанні про гарантію чи претензію, проханні про знижку, ДТП, запиті поза прайсом або прямому проханні покликати людину агент пише адміністратору і замовкає в цьому діалозі. У чаті на сайті поле вводу після цього ховається — обіцяти відповідь, якої не буде, гірше, ніж дати телефон.

**Агент: оцінка діалогу**

Коли розмова скінчилась — клієнт попрощався («дякую, все»), або заявку передано й питань більше немає — агент викликає `close_conversation`. Те саме робить команда `/finish` у Telegram і кнопка «Завершити чат і оцінити» в чаті на сайті. Після закриття клієнт бачить «Оцініть, будь ласка, спілкування» і зірочки 1–5: inline-кнопки в Telegram, кнопки прямо в чаті на сайті. Далі — «Дякуємо! Хочете додати коментар?» з кнопкою «Пропустити»; наступне текстове повідомлення зберігається коментарем.

**Оцінку приймаємо лише від клієнта, який назвався** — має бути і ім'я, і телефон. Анонімна зірочка нічого не дає: на одиницю нема кому передзвонити, а 90 днів до наступного прохання про відгук нема за ким рахувати. Анонімний діалог при цьому закривається як звичайно, просто без зірочок. Рішення приймається один раз, у момент закриття, і лягає прапорцем `ratable` у запис про закриття — щоб кнопка, натиснута через годину, не залежала від того, що сталося з карткою клієнта за цю годину. Перевірка стоїть і на сервері (`recordScore` віддає `not_identified`), а не лише в тому, що віджет не намалював зірочки.

Кнопка «Завершити чат і оцінити» в чаті на сайті з'являється під полем вводу рівно тоді, коли клієнт уже назвався, і зникає після закриття. Рішення про показ ухвалює сервер (`can_finish` у відповіді `/api/chat`), а не браузер.

Одна оцінка на діалог. Перше натискання виграє: повторне (клієнт передумав або Telegram надіслав callback двічі) не змінює ні бал, ні лічильники, ні вже надіслане адміністратору. Унікальність тримається самим ключем `astor:rating:<conversation_id>`, а не перевіркою в коді.

Оцінка 1–2 йде адміністратору негайно, окремим повідомленням, із каналом, телефоном клієнта і готовою командою `/reply`. Коментар, який клієнт допише пізніше, доїжджає другим повідомленням. Клієнт, незадоволений щойно, і клієнт, незадоволений із вчора, — це дві різні розмови, і друга вже майже напевно не відбудеться.

Після закриття діалог не продовжується: наступне повідомлення клієнта починає новий, без старої історії. Інакше агент вітав би людину відповіддю на питання, якого вона більше не має.

**Після виставленої оцінки чат на сайті замикається.** Поле вводу зникає, замість нього — рядок «Розмову завершено» і кнопка «Почати нову розмову». Причина не косметична: написати після оцінки означало б почати новий діалог, у якому висить блок оцінки попереднього, і клієнт не розуміє, чому бот не пам'ятає розмови, яку бачить на екрані. Кнопка бере нову сесію (новий `session_id`, тобто новий ключ діалогу на сервері) і чистить лог — модель не побачить ні рядка з попередньої розмови. Коментар це не блокує: для нього своє поле всередині блоку оцінки.

Механізм «наступне повідомлення — це коментар» лишився **тільки в Telegram**, де окремого поля немає. На сайті коментар іде в `/api/chat/rate` з явним `conversation_id`, який звіряється з сесією так само, як бал. Раніше прапорець очікування працював на обох каналах, і це був баг: клієнт, що після оцінки перезавантажив сторінку й поставив нове питання, отримував на нього «дякую, передав майстерні», а саме питання лягало в `comment`.

**Агент: відгук у Google**

Після оцінки 4–5 бот пропонує залишити відгук і дає кнопку-посилання. Потрібен `GOOGLE_REVIEW_URL` — адреса форми відгуку профілю майстерні. Не задано — кнопки просто немає: неправильна адреса відправила б клієнта писати відгук не тій майстерні.

Одному клієнту — не частіше ніж раз на 90 днів. Квота рахується за `customer_id` (ключ `astor:review:offered:*` з TTL 90 днів: саме його існування і є правилом). Для безіменного відвідувача сайту, який не назвав телефон, `customer_id` ще немає — там ключем стає канал і session_id. Відлік обнулиться з новою сесією, але альтернатива — просити відгук у кожного анонімного гостя щоразу.

Трійка посилання не отримує: 3 — це не «сподобалось».

**Агент: нагадування про планове ТО**

Інтервали лежать у `content/business.json`: `service_interval_months` (6) і `service_interval_km` (10000). Файл правиться без програміста, але вимагає деплою — читається раз за життя функції, як і FAQ.

Строки рахуються в один момент: коли адміністратор закриває заявку командою `/done <id заявки>`. Тоді в авто записуються `last_service_at`, `last_service_mileage_km` і розраховуються `next_service_due_at` (+6 місяців) та `next_service_due_km` (+10 000 км). Id заявки стоїть останнім рядком у повідомленні про неї.

`/done` — єдине джерело факту «роботу виконано». Автоматичної звірки з календарем немає, бо немає й календаря: час візиту тут призначає адміністратор телефоном, подій, які можна було б перевірити «подія в минулому і не скасована → done», не існує. Практичний наслідок: **не закрили заявку — не буде ні строку ТО, ні нагадування.** Варто взяти за звичку закривати заявку одразу після видачі авто; `/requests` показує, що лишилось відкритим.

Щоденний крон `GET /api/jobs/service-reminders` (07:00 UTC — 10:00 за Києвом улітку, 09:00 узимку; потрібен `CRON_SECRET`) бере авто, яким ТО не далі ніж через 7 днів, нагадування яким не надсилали або надсилали понад 30 днів тому, без відмови від нагадувань і з telegram_id у клієнта. Останнє — не формальність: у чаті на сайті немає куди надіслати повідомлення людині, яка його не відкрила. Таких авто `/service_due` показує з позначкою.

Повідомлення: «[Марка модель], останнє ТО було [дата]. Схоже, час на планове обслуговування. Записати вас?» і три кнопки:

- **Записати** — відкриває новий діалог із контекстом (авто, причина: планове ТО) і питає, коли зручно. Модель на натискання кнопки не викликається: питання ще не задане. Відповідь клієнта йде вже в агента, і той створює заявку, не перепитуючи ім’я й телефон.
- **Нагадати через місяць** — зсуває `next_service_due_at` на 30 днів **від попереднього строку**, не від «зараз»: інакше клієнт, що відклав нагадування за тиждень до строку, отримав би наступне вже з простроченим ТО.
- **Не нагадувати** — ставить `service_reminders_opt_out` і прибирає авто з черги.

`service_reminder_sent_at` ставиться лише після успішної доставки. Нагадування, яке не дійшло (клієнт заблокував бота, Telegram відповів 5xx), вважалося б надісланим, і наступна спроба була б через 30 днів — тобто вже після строку.

Пробіг агент дізнається тільки з розмови: телеметрії немає. Названий пробіг зберігається через `save_customer`, і якщо він переступив `next_service_due_km`, інструмент повертає моделі `service_due`, а та одним реченням пропонує записатись. Один раз за діалог, без наполягання.

У `callback_data` кнопок їде лише `vehicle_id`, без `customer_id`. Межа Telegram — 64 байти, два UUID це 73; але головне, що власника видно з chat_id, і пошук авто серед авто цього клієнта — це водночас і перевірка прав. Передай ми `customer_id` кнопкою, його можна було б підмінити.

**Агент: перевірка і витрати**

`npm run chat` — діалог у терміналі. Потрібен лише ключ Claude: без Redis сховище живе в пам’яті процесу, без Telegram заявки й handoff друкуються в консоль. Команди в CLI: `/new`, `/dump`, `/exit`. Це основний спосіб перевірити поведінку перед тим, як пускати агента до клієнтів.

`npm test` покриває те, що ламається тихо: розбір прайсу, обрізання історії, дедуплікацію клієнтів, схеми інструментів, те, що верхня межа ціни не просочується в промпт, закриття діалогу з оцінкою, правило 90 днів для відгуків і всю логіку нагадувань про ТО (кого вибрати, що нагадування не дублюється, що кнопки працюють і що чуже авто ними не зачепиш). Claude і Telegram у цих тестах підроблені — жодного платного запиту.

`npm run test:dialogs` — окремий набір, який звертається до справжнього Claude API і перевіряє не наш код, а рішення моделі: чи зрозуміє вона з промпту, що «дякую, все» — це кінець розмови, і що «Скільки коштує заміна масла? Дякую.» — ні. Без `ANTHROPIC_API_KEY` тести пропускаються, тож `npm test` лишається безкоштовним і детермінованим. Модель не детермінована: падіння тут означає «промпт прочитали не так, як ми думали», і це привід перечитати відповідь у виводі, а не одразу правити код.

Перед релізом усе одно пройдіть кілька реальних розмов із телефону.

Орієнтовний бюджет: близько $10–20 на місяць при 300 діалогах. Системний промпт (~9 КБ: правила, прайс, FAQ) кешується, а поточний час винесений в окремий некешований блок — без цього кеш не влучав би ніколи і кожне повідомлення коштувало б як перше. Vercel Hobby і Upstash free tier — $0.

Ліміти чату: 20 повідомлень на сесію за 10 хвилин і 200 на IP за годину; у Telegram — 30 повідомлень на користувача за хвилину. За кожним повідомленням стоїть платний запит, тож ці числа бережуть рахунок.

Щоденний звіт приходить адміністратору о 17:00 UTC — це 20:00 за Києвом улітку і 19:00 узимку; Vercel запускає крони за UTC. У звіті: діалоги, повідомлення, заявки, handoff, закриті агентом, кількість оцінок із середнім балом, окремо кількість низьких (1–2) і скільки надіслано запрошень на відгук. Середнє рахується при формуванні звіту: у Redis лежать кількість і сума балів, бо середнє не додається інкрементом. «0 діалогів» другий день підряд означає зламаний webhook або ключ, і звіт про це прямо пише. Потрібен `CRON_SECRET`.

**Крони**

Vercel Hobby дозволяє два крони, і зайняті обидва:

- `/api/jobs/service-reminders` — 07:00 UTC, нагадування про планове ТО;
- `/api/jobs/daily-report` — 17:00 UTC, щоденний звіт.

`/api/jobs/retry` свідомо лишений **без крона**. Третього слота на Hobby немає, а з трьох задач ця єдина має робочу альтернативу: повтор доставки заявки запускається вручну в адмінці, тоді як нагадування і звіт зробити руками нема кому. Сам ендпоінт працює як раніше — якщо захочете автоповтор, викличте його зовнішнім планувальником із `Authorization: Bearer <CRON_SECRET>`; це навіть точніше за Hobby-крон, який запускається в межах години від указаного часу.

Практичний наслідок: заявка, яку не вдалося доставити в Telegram, лежить у статусі `pending`, поки хтось не натисне повтор в адмінці. Вона не втрачена — але й не поїде сама. Якщо Telegram падає частіше, ніж хочеться стежити, це перший привід перейти на Pro і повернути крон у `vercel.json`.

Збої Claude API адміністратор бачить у Telegram: недійсний ключ, 400 і 5xx надсилаються окремим повідомленням. Клієнт у цей час отримує телефон майстерні, а не текст помилки.

**Агент: технічні нотатки**

Webhook Telegram відповідає 200 одразу, а обробку доручає `waitUntil` із `@vercel/functions`. Відповідь агента триває 5–20 секунд; без цього Telegram вважав би оновлення недоставленим і надсилав його повторно, а клієнт отримував би дубль. Через це `maxDuration` функції піднято до 60 секунд.

Віджет (`public/widget/chat.js` + `chat.css`) написаний під CSP сайту: `script-src 'self'; style-src 'self'`. Тому стилі окремим файлом, а не рядком у JS, і жодного `innerHTML` — відповідь моделі вставляється лише через `textContent`.

Кнопка «Залишити відгук» — єдиний `<a>` у віджеті, і їй доводиться перелічувати колір для кожного стану (`:link`, `:visited`, `:hover`, `:focus`, `:active`). Сторінка має глобальне `a:hover { color: var(--accent) }` зі специфічністю 0,1,1, що вище за просте `.astor-rate-review` (0,1,0): без цих рядків текст кнопки на наведення ставав червоним на червоному фоні й кнопка з вигляду порожніла.

Запити віджета підписує сервер, а не браузер. На старті віджет бере токен сесії (HMAC від session_id і часу видачі, TTL доба), секрет лишається на сервері. План передбачав HMAC у браузері, але для віджета з нашого ж домену це означало б секрет у коді, доступному кожному відвідувачу. Справжній захист тут — ліміти вище.

Токен лежить у localStorage, тож перезавантаження сторінки не починає розмову спочатку: віджет повертає його в `POST /api/chat/session` і отримує той самий діалог плюс останні 20 видимих реплік. Виклики інструментів і їхні результати у віджет не віддаються — лише те, що було сказано словами. Якщо токен протух або підроблений, видається нова сесія, а не чужа: історія йде за session_id, який підписали ми. Після handoff відновлений чат одразу показує телефон і ховає поле вводу.

Дані агента лежать у тому самому Redis: клієнти (`astor:customer:*`, з індексами за телефоном і telegram_id), діалоги (`astor:conv:*`, TTL 60 днів), заявки (`astor:request:<id>` плюс список id `astor:agent:requests`), оцінки (`astor:rating:<conversation_id>`), лічильники звіту. Авто зберігаються масивом усередині клієнта: у Redis немає JOIN, а авто поза власником не читається жодним сценарієм. Телефон у E.164 — ключ дедуплікації, тож клієнт, що писав у Telegram, а потім на сайті, впізнається як той самий.

Два місця, де структура не виводиться з даних, а тримається окремим індексом:

- `astor:conv:closed:<conversation_id>` — запис про закриття діалогу. Кнопка оцінки приходить із `callback_data`, де є лише `conversation_id`, а діалоги адресуються каналом і зовнішнім id; запиту «знайди за полем» у Redis немає.
- `astor:service:due` — ZSET черги ТО, score = дата наступного ТО, member = `<customer_id>:<vehicle_id>`. Без нього крон мусив би щодня читати всіх клієнтів до останнього, щоб знайти кілька авто. Авто з відмовою від нагадувань і без дати ТО в черзі не лежать узагалі — інакше правило «не нагадувати» трималося б лише на тому, що хтось не забув його перевірити при вибірці.

Заявки лежать під власними ключами, а список тримає лише id: Redis-список адресується позицією, а не id, і оновити в ньому одну заявку (`/done <id>`) неможливо. Список читає обидва формати — і id, і повні записи з часів до розділення, — тож заявки, створені до цього деплою, лишаються видимими в `/requests`.

Обрізання історії ніколи не розриває пару `tool_use` / `tool_result`: осиротілий `tool_result` — це 400 від API. Якщо безпечного місця для розрізу в межах ліміту немає, лишається більше повідомлень, ніж ліміт. Довготривала пам’ять (ім’я, телефон, авто) живе в Redis, а не в історії, тож обрізання її не торкається.

Текст клієнта ніколи не потрапляє в системний промпт — саме це й захищає від промпт-ін’єкцій: правила живуть у `system`, клієнт пише в `messages`. Усі інструменти оголошені зі `strict: true`, тож API гарантує відповідність схемі; невідомі поля не доїдуть до сховища. Телефони в логах маскуються до останніх 4 цифр.
